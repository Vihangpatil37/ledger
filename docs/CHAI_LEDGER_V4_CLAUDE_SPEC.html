1. Executive Summary & Domain Primer

Chai Ledger V4 is a zero-cost, high-leverage personal accounting and credit tracking web application engineered for Indian retail shopkeepers, tea stalls (chaiwalas), local merchants, and individuals managing daily khata (bahi-khata). It operates entirely on free-tier infrastructure (MongoDB Atlas M0 512MB, Vercel Hobby, zero paid third-party APIs) while delivering sub-50ms query responses, strict zero-float financial precision, and offline-resilient ergonomics.

Core Customer Ledger Invariant: In Chai Ledger's accounting model, customers can only owe the owner, or customers deposit advance money ("Jama") with the owner. The owner never incurs personal debt to customers. Outward repayment links for contacts are intentionally prohibited; all QR codes and UPI settlement links exclusively route funds into the shop owner's account.

Key Domain Concepts:

  • Udhar (Gave): Money lent, chai served on credit, or goods delivered on credit. The contact owes the owner this amount. Represented in traditional crimson accounting ink (#b93826).
  • Jama (Customer Advance / Deposit): Money received from the customer. If the customer returns previous Udhar, it reduces their debt; if they provide advance payments or excess funds, it is held safely as an advance deposit (Jama). Represented in calm emerald green ink (#246645).
  • Running Balance: Calculated deterministically as: 
    Running Balance = Total Udhar (Gave) - Total Jama (Received)
    • Balance > 0: Customer owes owner ("Baaki Udhar" / Debtor). Displayed in crimson red.
    • Balance < 0: Customer has advance deposit ("Advance Deposit / Jama"). Displayed in forest green.
    • Balance == 0: Account is fully balanced ("Chukte / Settled"). Displayed in neutral ink.

2. System Topology & Request Lifecycle

Chai Ledger V4 follows a streamlined, single-hop Next.js 15 App Router architecture. It deliberately avoids heavy microservice abstraction or intermediate REST dispatchers, executing all business logic directly within React Server Components and authenticated Server Actions.

Component File Path Responsibility & Operational Contract
Auth Middleware src/middleware.ts Edge-compatible route protector. Inspects stateless ledger_session JWT cookie. Redirects unauthenticated requests to /login while preserving destination in next parameter. Bypasses static assets and API routes.
Server Actions src/actions/*.ts All state-mutating transactions (create/edit/delete entry, create/update/delete person, update owner UPI profile). Runs authenticated with getOwner(), validates payloads via Zod, and issues targeted revalidatePath() cache updates.
Single-Trip Readers src/server/readers.ts Read-only aggregators. Replaces slow client-side multi-query waterfalls with single-round-trip MongoDB aggregation pipelines (e.g. $facet for debtor/creditor counts and overdue identification).
Client Shell & i18n src/app/(app)/layout.tsx Renders desktop sidebar, mobile top header, and mobile bottom navigation. Reads ledger_lang cookie on server to initialize LanguageProvider without client hydration mismatch.
Database Gateway src/lib/mongo.ts Global cached MongoClient singleton across serverless invocations. Handles replica set transactions with retry logic.

Indexes & Multi-Document Atomic Transactions:
  • users has a unique index on email.
  • people has compound index { ownerId: 1, name: 1 }.
  • entries has compound indexes { ownerId: 1, personId: 1, createdAt: -1 } and { ownerId: 1, dueDate: 1 }.
  • Deleting a person invokes a MongoDB replica-set transaction deleting the people record and all linked entries atomically. If transactions are unsupported (standalone MongoDB in local test), it falls back to ordered two-phase execution.

5. Zero Float Drift Precision Model

Floating-point representations in computing inherently introduce rounding errors (e.g. 0.1 + 0.2 === 0.30000000000000004). In financial ledgers, cumulative floating point drift will corrupt balance reconciliation, cause customer disputes, and fail accounting audits.

The Absolute Precision Rule: All monetary balances, transaction values, and settlement amounts stored in MongoDB Atlas are integers representing Indian Paise (1 Rupee = 100 Paise). Fractional cents do not exist. User-facing inputs and wire transfers use fixed decimal strings (e.g. "250.50"). Float math is strictly banned in all calculations.

6. Overdue Loan Engine & Timezone Mechanics

6.1 Asia/Kolkata (IST / UTC+5:30) Timezone Anchoring

Vercel serverless functions run on UTC hardware clocks. Indian users operate on Indian Standard Time (IST / UTC+5:30). If calendar calculations evaluated UTC new Date(), loans due on a given day would incorrectly flip to "Overdue" 5.5 hours early (at 6:30 PM the previous evening). 

// src/lib/due.ts - Exact IST Calendar Resolution
const nowUtc = new Date();
const istOffsetMs = 5.5 * 60 * 60 * 1000;
const istNow = new Date(nowUtc.getTime() + istOffsetMs);
const todayIso = istNow.toISOString().slice(0, 10); // "YYYY-MM-DD" in IST

6.2 Repayment-Aware Overdue Detection

A critical innovation in Chai Ledger is that a past-due loan entry does NOT trigger an overdue alert if the borrower has already paid back enough total money to cover it.

Algorithm (FIFO Loan Coverage Principle): When inspecting whether a contact is overdue:
  1. Sum all repayments: totalRepayments = ∑ RECEIVED.
  2. Filter all past-due loans: overdueLoans = entries.filter(e => e.type === "GAVE" && e.dueDate < todayIso).
  3. Sum overdue loan amounts: totalOverdue = ∑ overdueLoans.
  4. If totalOverdue > totalRepayments, the contact is flagged as Overdue.
  5. Chronologically iterate past-due loans to identify the exact oldest un-repaid loan and compute exact days overdue for display and WhatsApp reminders.

7. Security, Authentication & Query Isolation

Authentication is app-owned, zero-dependency, and edge-ready:

  • Stateless JWT Cookie (ledger_session): Signed with HS256 HMAC using a 256-bit secret (SESSION_SECRET). 30-day max age, HttpOnly, SameSite=Lax, Secure in production.
  • Constant-Time Timing-Attack Defense: On login, if an entered email does not exist in the database, the server computes a dummy bcrypt hash against a static string before returning "Invalid email or password". This equalizes execution time between existing and non-existing accounts.
  • Open-Redirect Defense (safeNextPath): Post-login redirect targets are strictly validated: must begin with a single /, cannot begin with // (protocol-relative URLs), cannot contain control characters, and cannot escape to external domains.
  • Mandatory Query Isolation Invariant: Multi-tenancy is enforced deterministically. Every query, mutation, and aggregation in the codebase MUST include { ownerId: owner }. No user can ever view, rename, edit, or delete another user's contacts or ledger entries.

13. Claude Feature Extension Playbook

The Non-Negotiable 6-Step Feature Implementation Protocol for Claude

When implementing any new feature in Chai Ledger, Claude must strictly follow this exact 6-step checklist in order. Never skip steps, never introduce floating-point math, and never omit test coverage.

  1. Step 1: Domain & Schema Types (src/lib/types.ts)

    Define clear TypeScript interfaces or enums. If the feature persists data, add the optional/required fields to Person, Entry, or User types. Always store monetary quantities as number representing paise (integer).

  2. Step 2: Zod Validation Contracts (src/lib/validation.ts)

    Create strict Zod schemas with sanitized string inputs, min/max bounds, and descriptive error messages. If parsing monetary input from a form, parse as a number in rupees and ensure positive values.

  3. Step 3: Server Actions & Data Readers (src/actions/ & src/server/readers.ts)

    Implement the backend logic with mandatory session verification: const session = await requireSession(). Always include ownerId: session.userId in every query and mutation filter. Revalidate affected paths using revalidatePath().
